The model

A wyrm threat model is an Open Threat Model (OTM) file — seven kinds of object that reference each other. Here's what each is, how they connect, and — the part that trips people up — who fills each one in.

Who fills what

Three sources populate the model, and it's worth knowing which is which:

  • Auto-detected by wyrm init — the structure (components, trust zones, and — where the source allows — dataflows and control mitigations).
  • You annotate — the context infra can't encode: which data is sensitive, what talks to what, how access is provisioned. Via annotations (.threatmodel/data.yaml or inline comments) or by editing the model.
  • Computed by wyrm analyze — the findings. These are derived from everything above and the rule catalogue; they are not stored in the file, so they're never stale.

The seven objects

ObjectWhat it isReferencesFilled by
projectName/owner of the system being modeled—init
trustZonesSecurity boundaries, each with a trustRating 0–100 (internet≈10, private≈80)—init (network/zone resources)
componentsServices, datastores, gateways, identities — the nodesparent.trustZone → a zone · assets → assetsinit
assetsThe data worth protecting, with CIA ratings 0–100referenced by components & dataflowsyou (sensitivity isn't in infra)
dataflowsTraffic between components — the edges. Tags like tls mark encryptionsource/destination → components · assets → assetsinit (compose/k8s) · you (Terraform, via flows:)
mitigationsControls that reduce risk (WAF, auth, encryption). Link one with appliesTo (element ids) + riskReduction 0–100 and analyze down-ranks matching findings — 100 resolves them. addresses scopes it to specific rules so a WAF can't mute an encryption findingappliesTo → components/dataflowsinit (detected WAF/Armor, untargeted) · you (link + rate)
threatsManually-declared threats. Findings are NOT here — analyze computes those—rarely used; usually []

So an empty assets: [] / dataflows: [] on a fresh Terraform baseline is expected — Terraform describes resources, not sensitivity or traffic. That's the annotation step. And threats: [] stays empty on purpose: your threats live in wyrm analyze, computed fresh every run.

How they connect

  A -.->|carried on| D
  M["mitigations"] -.->|reduce risk on| D

Amber = the bits you supply (assets, and — for Terraform — dataflows). Blue = derived, never written to the file.

How a finding happens

A rule reads the graph: e.g. a dataflow whose source and destination live in different trustZones, carrying an asset with high confidentiality, with no tls tag → WYRM-T001. Every input to that sentence is an object above. Miss the asset (sensitivity) or the dataflow (traffic) and the rule can't fire — which is why the annotation step matters, and why a bare Terraform inventory reports nothing until you add context.
