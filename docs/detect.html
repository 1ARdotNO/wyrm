Auto-detection

wyrm init reads your infrastructure-as-code and generates a baseline Open Threat Model — the topology, trust boundaries, and dataflows, inferred from what already describes your system. You review it and add the one thing code can't know: which data is sensitive.

How it works

wyrm init                          # auto-detect compose in the current dir
wyrm init --from k8s/               # a directory of Kubernetes manifests
wyrm init --from main.tf -o -       # print to stdout
wyrm init --from tfplan.json        # a Terraform plan (fully expands modules)
wyrm init --from ./chart            # a Helm chart (rendered via `helm template`)
wyrm init --from ./overlay          # a Kustomize overlay (rendered via kustomize)
wyrm init --from gitops/            # ArgoCD/Flux — follows each app to its local source
wyrm analyze                        # then find the threats in the baseline

🚢 GitOps: wyrm follows ArgoCD / Flux to the workloads they deploy

An ArgoCD Application or a Flux Kustomization/HelmRelease is a pointer, not a workload. wyrm reads the pointer's source.path (Argo), path (Flux Kustomization) or chart path (HelmRelease), resolves it against the scan root, renders that local Helm chart / Kustomize overlay / manifests, and folds the workloads into the model — so the app the pipeline actually ships is what gets analysed. A source in a remote git repo can't be followed offline: wyrm emits a note telling you to clone it locally and re-run, rather than silently dropping it.

🧩 Terraform modules: point wyrm at a plan for full resolution

Reading .tf directly, wyrm sees resources inside local modules but can't expand count/for_each or reach registry/git modules — the same blind spot every HCL scanner has. For a complete, collision-free picture, feed it the plan Terraform already resolved:

terraform plan -out=tfplan
terraform show -json tfplan > tfplan.json
wyrm init --from tfplan.json

Every resource then arrives with its module-scoped address (module.data.google_sql_database_instance.main) — modules unnested, instances expanded, nothing lost to name collisions. Same detection rules, exact topology.

Reading raw .tf without a plan still works for multi-module and multi-env layouts: wyrm walks every .tf file and, when the same resource name appears in two different module directories, path-qualifies the colliding ids (envs-prod-aws_db_instance-main vs envs-dev-…) so neither is clobbered. Names unique to one directory keep their clean id.

It writes .threatmodel/<project>.otm.yaml. Two principles guide every rule:

  • Defaults favor exposure. If a load balancer's internal flag is absent, it's treated as internet-facing — because that's the provider default. wyrm errs toward flagging exposure, not hiding it.
  • A WAF is a mitigation, not a wall. Detecting Cloudflare, Cloud Armor, or a Next-Gen WAF attaches a control to the ingress flow and downgrades the finding — it never makes it disappear. Detect-only rules (action = "log") don't count.

Annotate what it can't detect

A generated baseline captures structure. It can't know sensitivity (which data is PII), how access is provisioned, or which services talk to each other internally. You supply that context through annotations — two channels, one schema (full spec in ANNOTATIONS.md):

  • External .threatmodel/data.yaml, keyed by resource address — context without touching your infra code. Auto-loaded by wyrm init.
  • Inline comments next to a resource (Trivy-style), e.g. # wyrm: assets=pii provisioning=jit — context that lives with the code.

Precedence is inline > external > generated, and your direct edits to the .otm.yaml still win on merge — so it all composes and survives regeneration.

# .threatmodel/data.yaml
assets:
  - { id: pii, name: Customer PII, risk: { confidentiality: 100 } }
resources:
  google_container_cluster.workloads:
    assets: [pii]
    flows: [google_sql_database_instance.main]     # ← declare an internal dataflow
  google_project_iam_member.cluster_admin:
    type: identity
    provisioning: manual        # manual | approval | attribute-based | jit
    privilege: high

💡 The sleeper feature: flows

Terraform and the like describe resources, not the traffic between them — so a generated cloud model often has components but few edges, and STRIDE rules need edges to fire. The flows key lets you declare the internal dataflows the code can't express: flows: [db, cache] on a service says "it talks to these." Suddenly analyze has a graph to reason over — a sensitive flow crossing a trust boundary becomes a finding that simply wasn't visible before. It's the smallest annotation with the biggest jump in signal: a handful of flows: lines turns an inventory into a real data-flow diagram.
